## Как определяется расписание студента

Владелец приложения подтвердил, что сейчас каждому студенту назначается учебная группа. База подгрупп не ведётся. Для этой конфигурации достаточно связать действующее зачисление `student_enrollments.group_id` с `lessons.group_id`. Студентам одной группы доступно общее расписание. Назначения по подгруппам для обычной работы не требуются.

[Университет публикует расписание по группам](https://www.spbgasu.ru/students/raspisanie/). Проверенный импорт RASP заполняет группу занятия, дату, время, предмет, преподавателя и аудиторию. Активное зачисление студента связывает его с группой. В проверенных данных импорта, заголовках доступных ведомостей и метаданных CRM мы не нашли подтверждённого распределения студентов и занятий по подгруппам.

### Дополнительная проверка для будущих ведомостей

В [миграции](../../supabase/migrations/20261125203603_student_schedule_subgroup_audiences.sql) две независимые записи хранят основание каждого назначения. Оператору нужны утверждённый состав подгруппы и расписание с явной пометкой занятия.

1. Для действующего зачисления оператор вызывает `private.set_schedule_enrollment_subgroup(enrollment_id, roster_key, subgroup_code, source_ref)`. Ключ выделяет конкретный список, например практические занятия дисциплины за семестр. Ссылка или реквизиты ведомости передаются в `source_ref`.
2. Для подтверждённого занятия оператор вызывает `private.tag_schedule_subgroup_lesson(lesson_id, roster_key, subgroup_code, source_ref)`. Повторная запись с тем же ключом заменяет назначение. Общая аудитория в размеченном параллельном занятии отмечается кодом SQL `NULL`.
3. Неизменившиеся группа, дата, время, название и аудитория сохраняют привязку при замене серверного ID и преподавателя. Изменение даты, времени или названия требует сверки и обновления привязки вместе с исправленным расписанием. До повторной разметки отдельное занятие в новом слоте может попасть в общее расписание группы. Для автоматической обработки переноса требуется устойчивый идентификатор занятия у источника или явная запись о замене. При изменении аудитории в уже размеченном слоте новая аудитория ожидает подтверждения. Дубли с одной и той же аудиторией, временем и названием требуют уточнения источника.

Разделение внутри одной группы проверено только на синтетических ведомостях А и Б. Их данные существуют в изолированном тесте и удаляются по окончании. На рабочем сервере продолжает действовать прежний групповой RPC. Серверные изменения опубликованы как миграции в GitHub.

## Установка и повтор проверок

[Обновление ветки на Mac и запуск на iPhone](../../docs/MAC_IPHONE_QUICKSTART.md). Подпись и запуск на физическом iPhone требуют Xcode. На Windows проверен каталог iOS, все 19 записей ссылаются на непрозрачные PNG нужных размеров. [Новая иконка в Android](student_e2e_followup_20261125/android-launcher.png).

При работающем локальном Supabase Windows-команды `python scripts/qa_local_project_chat.py`, `python scripts/qa_local_timetable_backlog.py` и `python scripts/qa_local_student_news.py` запускают изолированные сценарии. Выполняйте их по очереди в одном рабочем каталоге. Для проверки новостей на прежнем контракте добавьте `--legacy` к команде новостей. Для DWG используется [драйвер Android CADView](../../scripts/qa_android_dwg_viewer.py). Тесты создают временные учётные записи. Удаление тестовых данных подтверждено в журналах выше.
