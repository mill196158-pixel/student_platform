# Варианты выпуска Student Platform

Дата проверки источников: 29.10.2026. Это технический план, а не заключение
о юридическом соответствии. Публичный режим пока не реализован и не выпущен.

## Рекомендация

Начать с полезного каталога примеров и инструментов без обязательной учётной
записи. Выбрать вариант A для самого простого пилота или B, если материалы
нужно обновлять без выпуска новой версии. Не копировать весь репозиторий в
«два приложения»: общие виджеты/модели остаются в student_ui и других пакетах.

## A. Локальный каталог без аккаунтов — минимум серверных зависимостей

1. Выбрать небольшой набор дисциплин и реальных частых задач.
2. Подготовить авторские/разрешённые разборы, шаблоны и калькуляторы.
   Очистить файлы и метаданные от чужих ФИО, подписей и зачёток.
3. Сделать отдельную публичную точку входа: каталог → поиск → материал →
   пример/расчёт. Контент включать в assets; избранное и история — на устройстве.
4. Эта сборка не должна инициализировать Supabase Auth, Firebase/push,
   presence, личные кэши и чаты. Не запрашивать лишние разрешения Android.
5. Проверить запуск офлайн, поиск, открытие файлов, формулы, крупный шрифт,
   слабый телефон, чистую установку и обновление поверх прежней версии.
6. Выбрать постоянный package ID и release-подпись, сохранить ключ вне Git,
   собрать подписанный APK и опубликовать по HTTPS для закрытого пилота.
7. После обратной связи — RuStore и/или Google Play.

Плюсы: нет обязательной анкеты, базы пользователей, серверных чатов или
зависимости входа от Auth. Минусы: обновления каталога требуют новой сборки,
большие материалы увеличат APK; нет синхронизации между устройствами.

Даже этот вариант не объявляем автоматически «вне 152-ФЗ». Проверить SDK,
системные резервные копии, телеметрию, поддержку, сайт раздачи, его access logs.
Если собственный сервис не получает данные пользователей, соответствующая
поверхность обработки существенно меньше; вывод подтверждается картой потоков.

## B. Одно приложение: гость + добровольный личный режим

1. Сначала сделать публичный каталог и отдельный API только опубликованных
   материалов; не открывать гостям старые таблицы и приватные RPC.
2. Поиск и чтение не требуют логина. Можно выбирать предмет вручную без
   обязательных ФИО, зачётки и группы. Избранное сначала локальное.
3. Разместить публичные материалы и инфраструктуру с учётом целевого рынка;
   составить карту логов/аналитики/идентификаторов и сроков хранения.
4. «Подключить личный кабинет» — отдельное добровольное действие. До него
   не запускать авторизацию, presence, push или подкачку личного содержимого.
5. Для личного контура: определить оператора, цели/основания, необходимые
   данные, размещение, документы, уведомления, удаление аккаунта и обработку
   обращений. Учесть требования локализации до сбора ПД граждан РФ.
6. Расписание/дневник подключить раньше социальных функций. Друзья/чаты/
   отзывы — после серверных ролевых тестов и модерации, в ограниченной бете.
7. APK-пилот → магазин → расширение по фактическим запросам студентов.

Плюсы: одно приложение и одна история установок, постепенный переход к личным
функциям. Минусы: сложнее проверять, что гость не запускает личные сервисы;
появление аккаунтов добавляет обязанности по данным и удалению аккаунта.
Наличие гостевого режима не отменяет требований для зарегистрированных.

## C. Публичное приложение и отдельная закрытая бета

1. Одна кодовая база, общие пакеты UI/моделей; две точки входа и конфигурации.
2. Публичная сборка — каталог и инструменты по варианту A или B, отдельный
   package ID, собственная подпись/конфигурация разрешений.
3. Закрытая сборка — существующие личные функции, только согласованные
   тестовые аккаунты и серверный allowlist. «Скрытая вкладка» не контроль доступа.
4. Разделить API, окружения, мониторинг и данные, исключить импорт production
   пользователей в публичный контур. Бета тоже требует законной обработки ПД.
5. Обе сборки проходят одинаковые проверки общих компонентов. Изменение пакета
   не принимается, если оно ломает одну из сборок.
6. После подтверждения спроса и готовности личного контура решить: оставить
   отдельный продукт или перенести добровольный кабинет в публичное приложение.

Плюсы: публичный выпуск проще изолировать от незавершённой социальной части.
Минусы: две сборки, обновления и карточки; переход аккаунтов сложнее. Два
package ID не являются юридическим освобождением от обязанностей оператора.

## Каналы Android

| Канал | Практический порядок | Ограничение |
|---|---|---|
| Прямой APK | release-подпись → HTTPS → инструкция установки → версионирование/обновления | Разрешение установки пользователем; обновления организуем сами |
| RuStore | кабинет → APK/AAB → карточка/документы → модерация → публикация | Правила площадки и цифровая подпись |
| Google Play | кабинет/верификация → AAB/подпись → карточка/Data safety → тестирование → заявка | Для новых личных аккаунтов: минимум 12 opted-in тестеров непрерывно 14 дней |
| Xiaomi GetApps | отдельный кабинет → сведения/сборка → модерация | Отдельно проверять поддержку страны и требования аккаунта |

APK ускоряет распространение тестовой версии, но не отменяет законов РФ,
авторских прав, защиты пользователей или правил Android. До публикации решить
страну и тип аккаунта разработчика; наличие аккаунта ещё не гарантирует допуск.

## Что обязательно проверить перед публичным APK

- Release signing не использует debug key; приватный keystore не в репозитории.
- Публичная сборка действительно не обращается к персональному контуру.
- Нет настоящих студентов/выгрузок в assets, исходниках публичного артефакта,
  логах или образцах. Не раздавать весь checkout архивом.
- Чистая установка, офлайн/плохая сеть, повторный запуск, обновление и возврат
  из фона; критические сценарии проверены на физическом Android.
- Материалы имеют понятное назначение, источник/право использования и дату
  проверки; решения и калькуляторы проверены на контрольных примерах.
- Политика данных описывает фактическую работу, включая сторонние SDK.
- Для аккаунтов — доступное удаление учётной записи и данных; предусмотрено
  восстановление доступа через настоящий канал, а не неработающий @student.local.
- Есть канал ошибок и обратной связи; решение о подключении новой аналитики
  принимается до сбора данных, а не задним числом.

## Очередность действий

Сейчас: закончить проверенный кодовый cleanup и зафиксировать локальный commit.
Затем выбрать A/B/C. Для быстрого пилота с минимумом анкетных данных — A.
Сначала проверяем полезность материалов, затем расширяем каталог. Не строим
массовый сбор студентов/групп до решения правового и инфраструктурного вопроса.
При необходимости онлайн-обновлений — B с отдельной публичной проекцией.
Существующие личные функции можно сохранить для закрытой беты по C.
