# Автоматическое тестирование пользовательских сценариев

## Выбранное направление

Владелец выбрал одну сборку: публичные материалы/сервисы без обязательной
регистрации, личные возможности после входа, сначала для тестовой группы.
Сейчас гостевой каталог ещё НЕ реализован, самостоятельная регистрация отключена.
Нужно сохранять текущие личные функции и добавлять публичный вход отдельно.
Тестовая группа допускается сервером, а не только видимостью кнопки.

Отсутствие регистрации не даёт автоматического освобождения от 152-ФЗ.
Гостевые SDK, журналы, идентификаторы, обращения в поддержку также требуют
проверки фактических данных. Закрытая группа не отменяет требований к обработке.
Источник: https://www.consultant.ru/document/cons_doc_LAW_61801/4f41fe599ce341751e4e34dc50a4b676674c1416/

## Что запускается сейчас

```powershell
cd C:\student_platform
flutter test
flutter test integration_test/anonymous_navigation_test.dart -d emulator-5554
cd admin_console
flutter test
cd ..\packages\student_ui
flutter test
```

Integration test запускает настоящий main и использует настоящие виджеты,
маршрутизатор и Android-плагины. Preferences подменены пустым тестовым хранилищем:
сохранённый аккаунт устройства не используется. Это не тест сохранения сессии.
Невалидные поля не отправляются в Auth. Firebase startup может обращаться в сеть.
Тестовая APK устанавливается на эмулятор вместо обычной debug APK; после теста
для обычного использования нужно снова выполнить `flutter run -d emulator-5554`.

Сценарий: запуск → вход → пустые поля → короткий пароль → получение доступа →
возврат. Дополнительно восемь приватных маршрутов должны вернуть гостя на вход.
Проверка запрета маршрута НЕ проверяет функциональность самого приватного экрана.
Ожидания ограничены; бесконечная анимация кота не используется как критерий готовности.

Официальная документация: https://docs.flutter.dev/testing/integration-tests

правильность данных, прав доступа или отсутствие двойной отправки.

## Стенд

Владелец подтвердил: имеется только основной Supabase. Автоматические сценарии
создания сообщений/профилей/заявок на основном проекте не запускались.
Нужен отдельный локальный/тестовый backend с миграциями и синтетическими данными,
без копирования персональных данных production. Подключение через существующие
SUPABASE_URL/SUPABASE_ANON_KEY dart defines; service_role никогда не включается в APK.
Подготовка аккаунтов производится серверным fixture-скриптом; клиентские прогоны
используют обычные роли. Cleanup ограничивается созданным test run и стендом.

Перед выпуском: сценарии гостя и тестовой группы, отрицательные проверки API/RLS,
проверка реального устройства, release signing и повторная установка/обновление.
Сейчас Android release в build.gradle.kts использует debug signing — публикационный
ключ нужно настроить отдельно, автоматическая подпись случайным ключом не выполняется.
