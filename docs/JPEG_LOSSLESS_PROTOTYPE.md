# Lossless JPEG upload: prototype evidence

Status: research only. This is not linked into the app, and no repository dependency, server configuration, production image or user image was changed.

## Candidate

JPEG entropy coding can be optimized without recompressing image pixels: `jpegtran -optimize` works on the existing quantized DCT coefficients. The upstream documentation notes that marker copying must be specified separately. See [libjpeg-turbo usage](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/main/doc/usage.txt).

The prototype used `libjpeg_turbo_dart` 1.1.0 from the local package cache, executing its `tool/tran.dart` with `-optimize -copy all` using a separate generated package configuration. It has no runtime dependencies in its pubspec and declares Dart `^3.12.2`; this repository currently advertises Dart `>=3.4.0`. The current Windows environment has Dart 3.13.2, but the Mac toolchain has not been checked. The package describes JavaScript web as unsupported and web as WebAssembly-only; it is recent, has an unverified publisher, and is not endorsed by libjpeg-turbo. Its license and source provenance require independent review before adoption. See [package documentation](https://pub.dev/packages/libjpeg_turbo_dart).

## Synthetic local results

| Input | Original bytes | Optimized bytes | Reduction | Decoded RGB equal |
| --- | ---: | ---: | ---: | --- |
| Generated photo-like gradient/noise, 1600×1200 | 793,520 | 763,845 | 3.7% | yes |
| Generated high-contrast pattern | 134,737 | 69,187 | 48.7% | yes |
| Generated QR image | 14,570 | 6,976 | 52.1% | yes |
| Generated photo with EXIF orientation 6, ICC and synthetic APP13 | 794,737 | 765,233 | 3.7% | yes |

For the last image, EXIF bytes, ICC profile, orientation and the sequence of APP1–APP15/COM marker payloads matched. Pixel comparisons used Pillow's decoded RGB output. The QR image was generated by the project's existing `qr` package, but neither the original nor the result was tested with a real QR scanner. These synthetic results do not predict savings for the user's photographs or establish Android/iOS correctness.

## Conditions for a possible future implementation

Keep the local source untouched. Apply only to new chat uploads with an explicit fallback to the original on any warning, error, timeout, unsupported platform, metadata discrepancy or non-beneficial result. Bound input size, dimensions, decoded memory and time; cancel isolate work on cancellation. Preserve original MIME/name and report actual uploaded size. Do not optimize forwards or legacy restored attachments.

Before integration, reject or separately validate MPF/multi-image JPEGs, unsupported marker structures, digital signatures, trailing data, corrupted and truncated files. Verify all relevant metadata, color management and original orientation on a representative corpus; test actual QR scans and screenshots/drawings as well as photos. Audit the codec and supply chain and run Android/iOS tests. A change to the Dart minimum SDK or a WebAssembly-only dependency requires compatibility review; no such change has been made. Even successful lossless optimization may save only a few percent rather than reducing photographs to kilobytes.
